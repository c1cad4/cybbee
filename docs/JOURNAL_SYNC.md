# Журнал пасеки и синхронизация

## Что изменилось
Карточка улья связывает новые осмотры и задачи по постоянному `hiveId`, а не названию. Старые осмотры сопоставляются по названию только при одном совпадении; неоднозначные записи остаются в общем журнале. Поддерживаются события осмотра, обработки, матки и сбора мёда. Пустые показатели не превращаются в нули или диагнозы.

Настройки → «Синхронизировать изменения» запускает обмен после отдельного согласия. Передаются ульи, задачи, осмотры и четыре настройки; точка карты и остальные локальные данные исключены. Первый обмен объединяет записи с разными ID. Различающиеся записи с одинаковым ID требуют выбора. Последующие обмены используют трёхстороннее сравнение с последней успешной базой, привязанной к аккаунту через серверный SHA-256 scope. Сам scope не является авторизацией; права проверяются серверной идентичностью Sites.

Клиент получает текущий журнал, вычисляет изменённые записи и отправляет `POST /api/journal/sync` с `{revision, changes}`. Каждое изменение содержит collection, id, value; null обозначает удаление. Сервер проверяет данные и версию, затем атомарно сохраняет журнал и предыдущую версию в D1 batch. Несовпадение версии возвращает 409; клиент повторяет чтение и слияние до трёх раз. Устаревший PUT снимка отклоняется, чтобы старый клиент не перезаписал новые данные.

Сохраняются пять локальных копий перед обменом и десять предыдущих серверных версий. Локальная копия восстанавливается кнопкой в настройках; серверная история пока предназначена для технического восстановления, отдельный экран просмотра не реализован. Очистка браузера удалит локальные копии. JSON-экспорт остаётся важным независимым резервом.

## Ограничения
Обмен ручной, не фоновый. Передача изменений уменьшает размер запроса, но чтение и хранение пока используют полный снимок до 200 КБ; это промежуточный шаг к таблицам отдельных записей и курсору изменений. Один обмен ограничен 500 изменениями. Фото/вложения ещё не поддерживаются. Одновременные изменения одной записи разрешаются выбором полной версии, а не объединением отдельных полей. Несинхронизированные локальные изменения, сделанные во время сетевого запроса, сохраняются и требуют повторного обмена.

Валидация не является медицинской диагностикой. Сведения об обработке требуют препарата, страны и HTTPS-инструкции. Полноценные физические проверки нескольких устройств и потери сети ещё предстоят.

## Проверка
Тесты с отдельной SQLite-базой проверяют авторизацию, изоляцию владельцев, сравнение версий, историю и её ограничение. Клиентские тесты проверяют объединение независимых добавлений, конфликты редактирования/удаления, неизменённые записи и исключение местоположения из обмена. Browser QA выполняется на localhost с синтетическими записями; пользовательский журнал не изменяется.
